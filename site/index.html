The agent schedules. You are the interrupt.

sdlc is a Claude Code plugin that runs a software project for you — journeys, epics, specs, tickets, test-first code, review, merge — and reaches you only for the decisions that are yours.

/sdlc
continue the project
/sdlc <anything>
an idea, an answer, a verdict on a delivery
  • YouWhat you want, five kinds of question, and checking the result by hand.
  • An agentReads, writes, builds, judges. Ten roles, each on the model that fits it.
  • A scriptWhatever can be decided mechanically is. No opinion, no tokens.

A pipeline makes you the scheduler.

You know what comes next, you launch it, and you remember what was put off. Everything that went wrong with a chain of commands came from that one fact.

Before: you hold the project

  1. you: run the spec command
  2. agent: interviews you, writes a spec
  3. you: approve, run the ticket command
  4. agent: cuts tickets
  5. you: approve, run the implement command
  6. agent: builds
  7. you: work out what to test, and what you meant to do next

Now: the repository holds it

  1. you: say what you want, once
  2. script: read the repository, name the next action
  3. agent: take that one action, write the result back
  4. script: read the repository again
  5. …and round, until nothing is actionable

You are reached through a file inbox, in five defined cases. Everything else the agent decides — and writes down, so you can overrule it later.

One rule: the loop is stateless. The repository is the state.

No conversation has to survive. Any session — today's, tomorrow's, one that crashed halfway — reads the files, takes one step, writes the result. Status lives in frontmatter; nothing derived is ever stored.

Every turn starts with the same call. A script walks docs/ and applies eight rules, first match wins. The same repository always yields the same answer, and it costs no tokens to get it.

The orchestrator never reads source code. It holds the graph, hands pointers to subagents, and acts on the typed result each one returns. That is what lets one session run for hours.

Because the loop keeps nothing in its head, only one thing can stop it for good: a question only you can answer.

        init · no docs/agents/sdlc.json yet
        
Granting autonomy is a conversation.

        
The first /sdlc in a repository asks before it installs anything. It inspects the stack, the tests, and whether a push to main deploys. Then it settles the config in a single round of questions, installs the rule files, and writes the map agents navigate by.

        
The permission list is shown, then written — never the other way round. The deny list is what turns "an agent must not deploy" from a request into a fact.

        

          
You
Say yes, pick the settings, confirm the permissions.

          
Writes
docs/agents/ — config, formats, escalation, review and ticket rules, coding standards for your stack — and the map block in CLAUDE.md.

        

      


      

        intention · no journeys, or no epic
        
The one thing no agent can look up is what you want.

        
So it is asked once, thoroughly. On existing code the agent reads before it asks: explorers reconstruct the journeys the code supports today — entry points, data model, test titles — and play them back to you. The interview then covers only the gap.

        
The result is a list of journeys, each exists, partial or wanted. An epic is nothing more than bringing journeys to exists, and it is closed when the journey plays end to end.

        

          
Acts
explorer · haiku, in parallel, read-only.

          
You
Correct the playback, answer the interview, validate the journeys and the order of the epics. After this, nobody asks you what again unless it is genuinely open.

          
Writes
PRODUCT.md, docs/journeys.md, docs/roadmap/, and ARCHITECTURE.md — a harness that points to code and never describes it.

        

      


      

        plan-epic · an epic with no feature line
        
Cut the epic. Specify nothing yet.

        
An epic becomes an ordered list of features, each deliverable and demoable alone. Only the next feature gets a spec: the spec of feature two depends on the code feature one leaves behind. Epics are aspirations; the code is the truth.

        

          
Acts
explorer on the modules the journeys touch, then the orchestrator.

          
Writes
The epic's ## Features, and under ## Reworked whatever the code forced it to change, and why.

        

      


      

        spec · the next feature has no spec, or a draft
        
Draft first, ask after.

        
You react to a complete proposal instead of answering a questionnaire. An explorer reconciles the epic with the code; the spec-writer drafts the whole spec and sorts every decision into one of three piles.

        

          
PileExampleGoes to

          
            
Settled"We use the existing database."The spec, silently.

            
Taken alone"The receipt is plain text." — about how, cheap to undo.## Decisions taken, with the reason. You may veto later.

            
Yours"Do we refund in part?" — about what a user sees, or hard to undo.One inbox question each, with a recommendation.

          
        

        
The acceptance walkthrough — the steps by which you will check the feature by hand — is written now. A step that cannot be written is a hole in the spec.

        

          
Acts
explorer · haiku, then spec-writer · opus. Every later step inherits the spec's mistakes.

          
You
Answer the real questions. Approve the spec if spec_gate is always; with questions-only, a spec with no question approves itself.

          
Replaces
The interview before every spec, and "do these test seams match your expectations?"

        

      


      

        ticket · an approved spec with no tickets
        
A critic, not your gut feeling.

        
The ticket-writer cuts vertical slices with an honest dependency graph. A script proves the mechanical half — frontmatter, sections, cycles, every story carried by a ticket, every ticket tied to a story. An independent critic, which did not write the cut, checks eight rules written as tests with counter-examples: "Create the payments table" fails; "A booking can be paid by card and shows as paid" passes.

        
One revision, one recheck, then escalation. And a way out downstream: an implementer may hand a ticket back as too-big. Tickets are disposable, so re-cutting is cheap — which is why no human gate sits here.

        

          
Acts
ticket-writer · sonnet, sdlc-check-tickets, ticket-critic · opus.

          
Replaces
"Does the granularity feel right?"

        

      


      

        execute · a frontier of ready tickets
        
Four honest outcomes.

        
The frontier is every ticket whose blockers are done. Up to three implementers work it at once, each on one ticket, test-first, in its own worktree. An implementer always returns one of four outcomes — and pushing on past the point where one of the last three became true is the only bad result.

        

          
OutcomeIt returnsThen

          
            
doneCommits and the output of verify.The merger takes it, one at a time.

            
too-bigA proposed split.Re-cut, carry on.

            
blocked"The spec says X; the code makes X wrong."A how: decided and recorded. A what: your inbox.

            
failedA diagnosis.One retry by a fresh implementer holding it. Then your inbox.

          
        

        
The merger guarantees three things, or the merge did not happen. The feature branch is green after every merge — two tickets green apart can be red together. No existing test was weakened unless the ticket said why: sdlc-test-guard reports every modified test and every added .skip(. And the harness changed in the same merge, by one hand: implementers declare a new module or term, the merger writes it.

        

          
Acts
implementer · sonnet, merger · sonnet. The orchestrator alone writes statuses.

          
Survives
A dead session. An in-progress ticket with no live agent is an orphan: resumed from its branch, or put back on the frontier.

        

      


      

        deliver · every ticket done
        
The verdict is computed, not felt.

        
Two reviewers read the diff with fresh contexts and never see each other's: one asks whether it does what the spec says, the other whether it obeys the repository's written rules. A third agent plays the walkthrough for real — a browser, real requests, real commands — and keeps the evidence.

        

          The type of a finding decides whether it blocks. Nobody's opinion does.
          
FindingMust citeBlocks

          
            
spec-missing · spec-partial · spec-wrongThe spec line.yes

            
out-of-scopeThe hunk nobody asked for.yes

            
rule-violatedThe written rule, and its file.yes

            
acceptance-failedThe walkthrough step.yes

            
design-guidelineThe guideline.yes

            
smell—no — fixed if it sits in changed lines, else one line of debt.

          
        

        
No citation, no block. A blocking finding that quotes nothing is downgraded to a smell — a reviewer cannot block on taste, or invent a requirement you never wrote. One fix pass, a re-review of the blocking findings only, and only a reviewer lifts a finding.

        
Then sdlc-merge-gate answers. The orchestrator merges on that answer and on nothing else. One feature is one merge commit, so one command undoes it; verify runs again on main, and red means an automatic revert and an alert.

        

          
Acts
reviewer-spec and reviewer-standards · opus, acceptance-runner and fixer · sonnet.

          
You
Receive a delivery report: what was built story by story, each walkthrough step marked played-with-evidence or yours, the decisions taken alone, the debt, the command to undo. The loop does not wait for you.

          
Replaces
A human reading the review, and a menu at the end of a branch.

        

      


      

        close-epic · every feature delivered or dropped
        
Three green features can still make a broken journey.

        
The seams between features were nobody's ticket. So the journey is played end to end, on main, as one run — and it moves to exists on proof only. If it does not play, the epic stays open.

        
Every entry of the epic's ## Later gets an explicit decision: a new epic, another epic's feature, or dropped with the reason. It is the project's memory of what was put off; nothing in it disappears silently. A short retro then proposes — a recurring smell to promote into a written rule, a sentence that would have spared you a question, a harness pointer an agent was missing.

        

          
Acts
acceptance-runner · sonnet, then the orchestrator.

          
You
One batched proposal. A rule that will block every future merge, and what to work on next, are yours.

        

      

    

  






  

    
Your side of the loop.

    
Attention is the scarcest thing here, so the list of reasons to spend it is closed.

  

  

    

      
Five cases reach you. No others.

      
    
        
  1. An unanswered whatBehaviour a user will see has several reasonable answers, and nothing you wrote settles it.
    2. 
        
  2. An irreversible decisionA migration that drops data, a paid service, a public contract.
    3. 
        
  3. Your intention against the codeThe journey asks for X; the code makes X impossible, or several times the cost.
    4. 
        
  4. StuckA bounded cycle ran out: a ticket failed twice, findings survived the fix pass.
    5. 
        
  5. Out of boundsSecrets, deploying, spending, rewriting main. Never worked around.
    6. 
      

      
Telling what from how: could a person using the product notice the difference and object? Then it is yours. Could only someone reading the code? Then it is the agent's.

    

    

      
An inbox made of files.

      
One file per item in docs/inbox/. An item is a question you can answer in under a minute without opening the code: the question, a recommendation, what it blocks, what continues meanwhile. Answer in the file, or tell the agent. An answer is a decision, so it is copied into the spec — then the item is deleted. The decision survives; the task dies.

      
While an item is open, the script routes around whatever it blocks and works on something else.

      

        
TypeWhen

        
          
alertMain was reverted.

          
questionOne of the five cases.

          
approvalA gate you switched on: a spec to approve, a feature to merge.

          
acceptanceA feature was delivered; here is the walkthrough.

          
proposalEpic closure, a rule to promote, templates to update.

        
      

      
Your phone buzzes in three situations only: everything is blocked, the cap below is reached, or main was reverted.

    

  


  

    
The price of removing gates is that a misunderstanding is found later. An agent reviewing an agent shares its blind spots; your walkthrough is the only check in the loop that does not. So max_pending_acceptance — three by default — bounds how far the loop may run ahead of you. Past it, the loop pauses and says so.

Mechanical where possible. Judgement where unavoidable. Never mixed.

    
A reviewer's detection is judgement. Everything after it is not. Six small programs — Python, standard library only — hold the guarantees.

  

  

    
ScriptGuarantees

    
      
sdlc-stateThe single next action, derived from the files. Deterministic, read-only.

      
sdlc-check-ticketsValid frontmatter and sections, no cycle, no dangling edge, every story carried, execution order honest.

      
sdlc-check-harnessEvery path the map cites exists; every module in the code is on the map. The harness cannot drift either way.

      
sdlc-test-guardEvery existing test modified, renamed or deleted, and every skip marker added, is reported to the merger.

      
sdlc-merge-gateNo open blocking finding, every agent step passed with evidence inside the feature directory, harness true, verify green.

      
sdlc-lockOne session per repository, as a two-hour lease the loop renews each turn.

    
  

  

    

      
One writer per piece of shared state

      
Statuses, inbox, journeys, debt: the orchestrator. The feature branch, ARCHITECTURE.md, the glossary: the merger. A textual conflict is cheap; two agents naming one notion differently is not — and only an explicit declaration makes that visible.

    

    

      
A refusal beats an instruction

      
A hook refuses force-pushes, history rewrites and deleting main — matching the whole command, so git -C . push --force does not slip through — plus whatever your project adds to forbidden_commands. An agent under pressure can forget a rule. It cannot forget a refusal.

    

  






  

    
The loop is ours. The method is Matt Pocock's.

    
The plugin owns the sequence, the formats and the verdicts. How to interview, write a spec, cut tickets, do TDD, debug and review comes from mattpocock/skills.

  

  

    

      
methods/ holds verbatim copies of eleven of those skills, under their MIT licence. Agents read them as files; they are deliberately not registered as skills, so they never collide with your own.

      
Those methods assume a human is present. The loop runs unattended, so every place where a method turns to the user is replaced — the critic instead of the ticket quiz, the spec's testing decisions instead of confirming seams — and each replacement is recorded in methods/gates.json.

    

    

      
Staying current without being surprised

      
A weekly workflow syncs the copies with upstream and opens a pull request — never a push. An upstream change can add a human gate, and an unattended agent that meets one stalls or guesses.

      
No pattern recognises every way of writing "ask the human", so the guarantee is a hash: the registry records each method's digest as last read by a person, and the check fails for any method that changed since. A fresh sync is red by design, until someone reads the diff.
